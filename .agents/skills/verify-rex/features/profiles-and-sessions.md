# Profiles and sessions

Users select a profile in the first line of a request, perform permitted work and return to that profile's conversation without automatically mixing another profile's history.

## Preconditions and entry points

The normal user entry is `npm run sandbox -- rex` with an input beginning `profile: <id>` and a nonempty task; `--new-session` requests a fresh conversation. Normal sandbox calls may use paid models. Deterministic checks use invented fixtures and the disposable synthetic stack; model-dependent QA uses real inference under the root standing approval and low-cost model policy. Select QA models in isolated test configuration/state rather than changing active profile defaults.

## Repeatable checks

- Run `npm run test:profiles` for validated lookup, malformed/missing profiles, shared configuration/SOUL composition (including mandatory policy on legacy profiles), immutable concurrent scopes and cancellation.
- Run `node --import tsx --test tests/profile-provisioning.test.ts tests/sandbox.test.ts` for selected-only snapshots, symlink rejection and host launcher contracts.
- Run `node --import tsx --test packages/pi-profiles/tests/adapter.test.ts packages/pi-profiles/tests/boundaries.test.ts` for actual SDK tool effects, shared-default SOUL profiles, forced denied calls, separate/resumed/new histories, locks, failures and cancellation.
- Run `npm run verify -- sandbox` to build and exercise the installed `rex --new-session` command under synthetic inference, including selector rejection, cap-free requests, truncation reported on stderr with exit 1 and no partial stdout, and a successful resumed request. The suite also checks installed SDK response handling through a private loopback fake provider and asserts Pi's installed version and read-only runtime/package boundaries.

## Expected observations

A coding write produces the exact file contents and persists across workers. Research cannot read the coding profile's configuration or workspace: each worker gets only its own volumes and selected read-only snapshot. `qa` can run a shell check and still cannot read `coding`'s configuration or use the write tool. The fake provider verifies actual tool results, not a model claim of success. A resumed profile sees its own earlier marker, not the other profile's marker. New-session retains old history without loading it. Same-profile contention makes no second model call; independent profiles retain their own identity. Cancellation and ordinary failure release the turn lock.

Override tests prove a per-profile allowed model reaches the wire, a different catalog model is denied before inference, and the next request returns to its configured default. Installed acceptance exercises `--model` on a SOUL worker. Catalog tests verify selected output metadata, unlisted-model rejection before inference, and the Anthropic `/v1/messages?beta=true` path. Disposable acceptance seeds a catalog so provisioning must preserve it. Requests must not include a blanket output-token cap; an operator catalog may supply a per-model output limit. A provider-truncated answer rejects with `IncompleteProfileResponseError`, not successful partial output. Truncated tool arguments must not execute or trigger another inference request. A truncated final summary does not roll back earlier completed tool actions or automatically repeat them; the public message warns about those effects. The lock must be released and a subsequent user request must recover. Keep these cases as regressions, including empty length-stopped output.

## Gotchas and coverage limits

Installed worker acceptance now covers real writes, shell/read cross-profile denials, the `qa` shell isolation and denied write, separate volumes and process namespaces, simultaneous worker containers, host-lock/container-name contention, truncation/recovery, persistence and minimal SOUL profiles. The unprofiled baseline rejects the profile CLI. SDK-only calls do not establish filesystem isolation, and synthetic inference does not establish live-model quality. The normal master still does not seed shared defaults automatically; acceptance provisions invented shared configuration in its own master. Old shared data is not migrated. Abrupt operator or SDK termination can leave locks requiring specific recovery; never delete histories or auto-break locks. The explicit CLI guard was observed failing before implementation (the shared baseline returned status 0 instead of rejecting), then passing after the guard.

Fallback coverage: SDK tests inspect ordered wire requests, one user prompt in the retry, selected model persistence, next-request primary restoration, exhaustion, override-only failures, authentication denial, and truncation/tool-action no-replay. Installed acceptance triggers a synthetic pre-response 503 and checks chosen model plus attempt order. Real-model acceptance uses a controlled local 503 then Haiku through the existing gateway; this does not prove a real provider outage.

Reasoning checks verify all supported configured thinking levels, rejection of invalid levels or non-reasoning catalog candidates before inference, and exact reasoning_effort on both primary and fallback wire requests. Installed SOUL-worker acceptance asserts low effort. Live Haiku compatibility does not prove provider-internal reasoning or output quality.

Turn-limit checks exercise fieldwise defaults and invalid bounds; real writes before a request-budget abort; loaded-history refusal before inference; a stalled fake provider stopped by the deadline; lock release and recovery; limits preserved in selected snapshots and SOUL digests. Installed limits-check worker performs one tool action, hits its one-request bound, retains the file, and recovers in a new session.

Skills/templates: SDK assertions verify selected metadata appears before the skill body, actual read returns the body, unselected skills and workspace .pi resources stay absent, and explicit templates substitute arguments. Metadata/colliding names fail before inference. A selected skill cannot invoke the denied write tool. Installed worker checks skill advertisement then read and selected template output; live Haiku evidence must inspect successful read tool results rather than only final text.

Workspace opt-in: baseline project files stay absent with no references. After resources.workspaceInstructions opt-in, selected own-workspace text reaches the system message. A tool rewrite does not change the current turn; a fresh turn sees it. Core cases reject traversal, links, newlines and missing roots/files with redacted errors. Installed SOUL worker seeds only its own AGENTS.md and the fixture verifies its text. Live Haiku may verify following that selected text, not host/project discovery.

Installed extensions: core validates catalog IDs/hashes/tools; SDK tests prove explicit selection, integrity/root/symlink refusal before inference, all-before-any import preflight, catalog registration match, whitelist/blacklist and nested tool denial, plus no custom-tool grant expansion at approval. A lifecycle-hook counter proves fallback does not replay trusted code after a 503. Installed fixture produces an inspected private-workspace marker; nested write leaves its target absent. Live Haiku proof must inspect actual effects/results. Operator code remains trusted with full process authority, not sandboxed by these checks.
