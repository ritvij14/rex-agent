# Terminal sandbox

Scope: this experiment and its private Docker-managed state. Inherit the root and `lab/AGENTS.md` instructions. This is an interactive Pi environment plus a minimal profile-selected Pi SDK command, not Pi Durable, a web application, or a replacement CLI Proxy API.

## Boundary and ownership

The Dockerfile pins Node.js 22.23.1 by digest; the local manifest and lockfile pin Pi 1.3.0, tsx 4.23.15, TypeScript 7.0.2, and transitive dependencies for both services. `sandbox` runs Pi and shell commands as UID/GID 1000 with no external network interface, no host mounts, no published ports, no capabilities, a read-only root filesystem, 2 CPUs, 1 GiB memory, and 128 processes. Persistent application writes use `/workspace` and `/state`; temporary storage includes a bounded `/tmp` and Docker's container-local devices/shared memory. Its Unix-socket volume is read-only. `/opt/rex` owns immutable runtime code and installed tools. Locked file dependencies install `@rex/profiles` and `@rex/pi-profiles` from explicitly filtered package build contexts; never replace this with a checkout/home mount or upload unrestricted source directories. The unprofiled `sandbox` no longer mounts active definitions or proposals. `scripts/profile-worker.ts` is the operator-side launcher: each `rex` request creates a networkless, resource-limited worker with separate workspace, state, proposals and definitions-snapshot volumes. The first operator seed helper initializes the master `profile-definitions` volume from public image templates without replacing existing contents. `provision.ts` validates and copies only the selected profile plus shared configuration into its snapshot; other profile directories and arbitrary files never enter that volume. `/profiles` is mounted read-only with `nocopy`, preventing Docker from filling a fresh worker volume with every image template. The aggregate master is never mounted into an agent worker.

`gateway` runs separately as UID/GID 1000 with 0.5 CPUs, 256 MiB memory, 64 processes, a read-only root filesystem, and no host mounts or published ports. It owns the Unix socket and forwards only explicitly allowed inference requests to one fixed proxy origin. It must never become a general HTTP proxy. Client credentials, forwarding headers, URL overrides, management paths, redirects, and upgrades must not pass through. The sandbox has no access to the gateway environment or provider credentials. Model calls still consume the existing proxy's accounts and limits.

The production upstream is the existing Mac CLI Proxy API, reached through Docker Desktop's host connection. Do not change that proxy, read its credential stores, or copy host Pi settings. `REX_PROXY_API_KEY` is an optional inference-only client key supplied by the operator's environment to the gateway alone; never print it or run Compose config/inspect commands that expose it. Never supply a management key in place of an inference key. No other host environment variables are forwarded. Docker itself is trusted infrastructure; this is not a claim of protection against container-runtime or kernel exploits.

Operator helpers are short-lived Docker runs, not agent tools or normal services. Provisioning has only the `CHOWN` capability to initialize the selected writable volume roots; the seed and approval helpers have no capabilities. All helpers have no network, host mounts, inference socket, credentials or privilege escalation, a read-only root, and explicit CPU/memory/process limits. Create approval mounts the master writable and only the builder's proposal volume read-only. Update approval mounts only the target profile's proposal volume and locks that profile. Both validate a private temporary snapshot. Metadata cannot select another source volume. A profile file cannot grant `revise_profile`; only the host `--maintain` flag exposes it, and the draft cannot add tools. The original draft is retained read-only. Replay fails because the destination or base revision no longer matches.

The operator holds an exclusive host lock per profile for provisioning and the complete worker lifetime. Docker also reserves a deterministic profile-specific container name, protecting against an orphan worker after client interruption. Worker cleanup removes that exact container before releasing the lock. An abrupt operator crash may leave a host lock and/or worker requiring manual recovery after checking no turn is running; never auto-break locks. The in-adapter session lock remains an additional guard, not the isolation boundary. A model with `bash` can access its own container, but cannot see another profile's volumes, configuration, histories or private state. Docker/kernel exploits are outside this boundary.

The root and terminal manifests scope an exact `undici` 8.12.2 override to Pi Coding Agent 1.3.0. Regenerate each lockfile with npm, not hand edits; `tests/dependencies.test.ts` checks the locks and host resolution, and container acceptance checks the installed external copy. This is a partial SDK dependency mitigation: Pi's published CLI embeds a separate copy that npm overrides do not replace. Keep that limitation visible until a reviewed Pi release fixes its bundle; see [dependency mitigation](../../docs/features/repository-safeguards.md#external-pi-http-dependency).

## Commands

Run from the repository root:

- `npm run sandbox -- build`: build locked tools; the build requires public registry access, not accounts.
- `npm run sandbox -- start`: explicitly start the two services without making a model request.
- `npm run sandbox -- configure MODEL_ID API`: configure one model inside private state; API is `openai-completions`, `openai-responses`, or `anthropic-messages`.
- `npm run sandbox -- shell` or `npm run sandbox -- pi`: attach to the isolated shell or Pi. Pi is offline for automatic network activity and loads no inherited extensions, skills, prompts, or themes. Explicitly requested experimental resources still execute only inside the sandbox.
- `npm run sandbox -- refresh`: require an already running gateway, rebuild the image and recreate only `sandbox` with `--no-deps`. Preserve its volumes and the gateway's existing inference authentication; do not use `start` as an unattended refresh when the host key is absent.
- `npm run sandbox -- rex [--new-session] 'profile: <id>\n<task>'`: execute one explicit profile-selected request through Pi's SDK; use a real newline or stdin. Missing/unknown selectors fail before inference. Sessions resume only within the selected profile; `--new-session` creates a new history without deleting old ones.
- `npm run sandbox -- review-profile ID`: show a private draft and its canonical digest through the operator helper; never publish this output.
- `npm run sandbox -- approve-profile ID DIGEST`: explicitly activate that reviewed draft through the operator helper, without overwriting existing definitions. Do not execute merely because a model proposed it.
- `npm run sandbox -- stop`: remove this experiment's normal Compose services/network, not active independently launched workers; retain volumes.
- `npm run sandbox -- reset --confirm`: delete Compose-declared volumes only. Dynamically named per-profile volumes and legacy detached volumes are retained; their migration or deletion requires separately scoped approval. This destructive operation requires explicit user approval before execution.
- `npm run sandbox -- check`: build and run an isolated synthetic acceptance environment, test boundaries and restart behavior, and remove only that command's newly created test resources. It never contacts the live proxy or paid models.

After a refresh, the installed adapter can be checked without paid inference using `docker compose --env-file /dev/null --project-name rex-terminal -f lab/terminal/compose.yaml exec -T sandbox node --import /opt/rex/node_modules/tsx/dist/loader.mjs /opt/rex/packages/pi-profiles/src/verify.ts responses`. This mode serves fake replies on a private ephemeral loopback port, uses and removes only its own temporary workspace/history, and never uses the inference gateway. Confirm normal profile locks are idle before refreshing; preserve the existing gateway container and all named volumes.

Docker Desktop must already be running on macOS. The operator controls Docker from the host; neither service receives its socket. Necessary live inference QA is standing-approved under the root low-cost model policy, without per-run confirmation. Successful synthetic checks are not evidence of compatibility with the real account/model configuration; run real calls when that behavior needs verification. Credential access and account/proxy changes remain outside that approval.

## Tests and cleanup

`npm run check` typechecks this experiment and runs its deterministic gateway/configuration rejection tests alongside repository safeguards, without Docker or accounts. `npm run sandbox -- check` additionally tests the actual container boundary, resource settings, writable/read-only paths, forbidden networking, gateway denial without upstream access, synthetic inference, gateway interruption/recovery, and state survival across recreation. CI runs the synthetic acceptance command without secrets. Test-created volumes contain invented data only and are deleted by that command; normal experiment volumes are never deleted by tests.

Workspace, settings, profile definitions/drafts, sessions, and sockets live in this experiment's named Docker volumes, outside the clone. Workers own `<project>_rex-profile-<id>-workspace`, `-state`, `-proposals` and `-defs` volumes; shared baseline volumes and old profile data are not migrated into them. Synthetic acceptance verifies installed CLI guard rejection in the unprofiled baseline, real coding writes, shell/read cross-profile denials, independent concurrent workers, read-only snapshots, builder-tool-to-operator admission, and persistence. The SDK alone remains a library, not a sandbox; only operator-launched workers establish filesystem isolation. Its raw Pi TUI command remains a separate unprofiled baseline. Stopping is not resetting. Never upload volumes, logs, sessions, or account responses. New gateway routes or dependencies require successful and rejected-request tests before use. Changes to the execution boundary require updating this guide and the focused sandbox documentation.
