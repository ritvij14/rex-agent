# Profile mechanism instructions

Scope: this core package resolves explicitly selected profiles and binds one profile to an asynchronous turn. It is not a router, Pi adapter, model execution engine, authorization service, or filesystem sandbox. Inherit the root and `packages/` instructions.

## Public API and dependencies

`@rex/profiles` exports only `src/index.ts` through its package manifest. Consumers use that public export, not internal paths. The supported API is `lookupProfile`, `loadSharedConfiguration`, `resolveEffectiveProfile`, `ProfileRuntime`, `ProfileError`, definition/shared/request/ID validation, `isToolAllowed`, and their exported types. `parseProfileArguments` owns shared host/installed CLI flag parsing. `selectProfileModel` enforces the per-reference `overrides` allowlist and operator catalog membership without changing the profile. `src/configuration.ts` owns the pure schema/selector/policy/composition rules; `src/errors.ts` owns fixed diagnostics. The implementation owns filesystem reads and `AsyncLocalStorage`; it must not write profile state, inspect environment variables, change the working directory, or import Pi, Pi Durable, or provider SDKs. Only Node built-ins are required.

The caller supplies an absolute, trusted profiles root. A validated ID maps directly to its child directory; aliases and symlinked homes/definitions are rejected, and the ID `shared` is reserved for the operator-owned shared directory. Version-2 profiles hold persona/instructions in a regular bounded `SOUL.md` plus an optional `profile.json` with matching `id` and optional `model`/`tools` overrides (`SOUL.md` also replaces the requirement for `profile.json` on a minimal profile). Version-1 `profile.json` keeps the matching `id` plus an optional complete `configuration`; inline instructions and `SOUL.md` never mix. The shared directory's all-profiles persona file is `REX_SOUL.md`. Shared configuration combines defaults (replaced by profile whitelists) with unioned blacklists and a mandatory blacklist that profiles cannot weaken through composition. Shared `models` is an optional bounded operator catalog of exact model IDs, API, context/output limits, and reasoning capability. Entries cannot supply endpoints or credentials, and the array and entries are frozen. Do not silently accept configuration the package cannot enforce. Detailed behavior and limitations are in [the profile feature document](../../docs/features/profiles.md).

## Turn lifetime

Each runtime has independent asynchronous storage. `run` performs lookup itself so callers cannot supply a forged home. The profile record is frozen and cannot change within the turn. Nested turns on the same runtime are rejected. `current` must fail outside a turn, after its callback settles, and after its abort signal fires. Cancellation is cooperative: the callback must settle before `run` settles, and the package must not claim to terminate arbitrary work or revoke paths already obtained by a caller.

## Checks

Run these commands from the repository root:

- `npm run test:profiles` runs the package's tests through its public workspace export.
- `npm run typecheck` includes package sources and tests in the root strict no-emit check.
- `npm run check` includes the package tests, repository tests, privacy checks, and formatting; CI uses this command too.

Execution/typecheck tools are declared and invoked by the root package. This private source-only workspace has no standalone build, generated files, migrations, external services, or extra package dependencies. npm owns workspace links and lockfile updates.

Build contexts use a deny-by-default `.dockerignore` listing runtime sources/manifests explicitly; update it with real source ownership changes, never include tests, private state or arbitrary directories. Tool policy accepts exact names or the whole `*` rule, with blacklist precedence and no implicit grants; the adapter must enforce execution and host-approved tool availability.

Required regressions cover schema (versioned and legacy), shared configuration parsing/loading/failure codes, SOUL bundles (minimal, oversized, blank, symlinked, mixed-source), override composition with unioned and mandatory blacklists, incomplete resolution, mandatory first-line selectors and wildcard/blacklist precedence; valid and missing definitions; malformed/mismatched/unsupported configuration; invalid, traversal and reserved IDs; directory/definition symlinks; bounded regular-file reads; redacted errors; concurrent profile-specific file reads; missing/closed/nested scopes; exceptions and cancellation; and unchanged process environment/working directory. Use temporary synthetic profiles only, never real profile or account state.

Model references may contain bounded `fallbacks` and `overrides` ID arrays. `planProfileModels` returns an ordered catalog-validated plan, with no fallback when a request override is explicit. It does not execute providers or retry tool actions.

`TurnLimits` has bounded integer deadlineMs/maxRequests/maxHistoryBytes. Shared defaults merge fieldwise with profile overrides; version-2 uses top-level limits and legacy uses configuration.limits. Default constants are exported and immutable. Include version-2 limits in lookup, copying, and whole-bundle digests; configuration is invalid if any limit exceeds its hard bound.

`loadInstructionResources(root,id,paths)` uses validated profile lookup plus the existing bounded regular-file reader. It accepts only explicit lowercase resources/*.md paths, no scanning, links, or traversal, and returns frozen ordered path/text records. Bounds are eight unique files, 200 characters per path, 16384 bytes per file, and 65536 loaded bytes. Lookup and shared loading attach frozen resourceFiles from explicit resources.instructions; effective composition always includes shared files before own persona/files. validateResourceFiles binds ordered references to bounded path/text records for adapter writes. The adapter must include them in approval and snapshots, not rediscover them.

ResourceConfiguration supports explicit instructions, skills, prompts, and lazy references paths with a combined eight-file/65536-byte limit. resourcePaths preserves category then declaration order; validateResourceFiles binds every ordered path/text record. Lookup freezes all selected resourceFiles, but effective instructions include only resources.instructions, never lazy skill bodies or templates. Metadata interpretation belongs in the Pi adapter. resources.codemode is an optional frozen boolean selection, not a path or tool grant. resolveEffectiveProfile exposes codemode:true only when a shared or own selection enables it; own false cannot remove a shared true. Keep its reference in bundle/snapshot/digest handling without loading executable code in core.

resources.workspaceInstructions references dynamic files relative to the trusted own workspace, not the definition bundle. loadWorkspaceInstructions rejects unsafe paths/links, reads bounded regular Markdown, freezes results, and redacts errors. resourcePaths intentionally excludes these dynamic paths from bundle-file serialization; their reference list itself remains in the digest.

parseLocalMcpCatalog/localMcpToolNames/selectLocalMcpServers validate and compose shared localMcpCatalog plus explicit resources.mcp IDs. Required shared selections remain present; unknown IDs and combined bounds fail closed. resolveEffectiveProfile returns optional frozen mcpServers metadata separately from the text/model/tools configuration. Reject unsupported execution/auth fields, inherited required properties, normalization collisions and names exceeding Pi's 64-character bound. Copy/freeze arguments and tool arrays; arguments remain literal. Add the three common resource tool names once only when selected/catalog entries opt into resources; raw server-tool collision validation stays independent of those shared names. Reject collisions with extension-catalog tool names. Core must not launch a process or import Pi; adapters own actual code integrity, required connections, execution policy and cleanup.

Shared extensionCatalog validates bounded ID/integrity/tool metadata only; resources.extensions selects IDs independently from resourcePaths text files. Core never imports executable modules. Adapter import from an operator-installed immutable root, tool enforcement, and catalog matching are separate trusted execution responsibilities.
